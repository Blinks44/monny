# Plugged-in discharge: product and feasibility assessment

Reviewed 2026-11-16 at main `c25bea9` (1.7.0/build 94). Planning only: no app changes, helper install, native setting change, sleep assertion or SMC write. [APP-020](../tasks/APP-020-plugged-in-discharge-assessment.md) owns the decision/handoff. Existing main restrictions remain unchanged.

## Request and recommendation

Assess a single manual action that discharges a plugged-in MacBook to approximately 20%, restores adapter power and allows charging under the existing limit. No recurring sailing range, scheduling, artificial load or full calibration workflow. The requested health rationale (twice-weekly discharge) is not established by the reviewed evidence. Prefer the existing 80% native charge limit for desk use. Between the two investigated mechanisms, discharge is a narrower research candidate than quieter fan curves because its policy is simpler and Monny has historical groundwork; it is not a low-risk implementation promise. Do not select either for production until product value and hardware recovery are established.

A more defensible optional future action is a one-off reduction to the existing charge limit (for example 100% to 80%), then ordinary adapter operation. This changes the requested endpoint and requires user agreement; it is not silently substituted or implemented here.

## Battery-health evidence

- [Apple lithium-ion explanation](https://www.apple.com/batteries/why-lithium-ion/) says discharge before recharging is unnecessary, defines cumulative full-equivalent cycles and notes capacity loss with cycles. It does not recommend a twice-weekly 20% routine. Example arithmetic: two 80%→20% discharges weekly consume about 62 full-equivalent cycles annually (0.6 × 2 × 52), excluding other use. This counts throughput, not a prediction of capacity loss or a universal net-aging comparison.
- [Apple Mac optimization/charge-limit guidance](https://support.apple.com/en-us/102338) reduces time fully charged and provides an 80–100% target; macOS occasionally charges fully for estimation. Long-term high state of charge/temperature, cycle wear and state-of-charge estimation are different issues. No evidence reviewed establishes that this proposed routine improves longevity compared with using the existing limit. Do not market discharge as rejuvenation, necessary exercise or calibration.

## Mechanism and existing Monny evidence

Preventing battery charging does not force discharge: the Mac can keep drawing adapter power. Adapter isolation moves the Mac's workload onto the battery; consumption, not an artificial load, sets the discharge speed. At <=20%, restore and verify adapter input; leave the native charge target/optimization unchanged. Reconnection permits charging but cannot guarantee macOS starts charging immediately or an exact 20% floor.

Reviewed current BatteryTab/read-only SMC contracts plus historical AdapterVerificationOperations, BAT-027/028/030 on `experiments/discharge`. The old experiment used CHIE with journal/watchdog recovery and short fixed observations. On M1 Max/macOS 27.0.1, bounded source changes and restart/sleep/removal recovery were recorded; BAT-030 accepts one active checkpoint restoration before helper removal. These are historical evidence, not fresh tests. Sustained discharge to a target, client quit/crash, broad adapters/firmware and full physical behavior remain unverified. The helper source explicitly requires an independent physical-presence provider: current source flags can look unplugged during isolation, while cached adapter details can outlive cable removal. Never abandon recovery because telemetry says battery/unplugged. Do not merge the experiment wholesale into main.

## Current upstream review

- [AlDente features](https://apphousekitchen.com/aldente-overview/features/) describe one-off discharge to a charge target and explicitly disable sleep for clamshell discharge. This demonstrates a product mechanism, not an SDK, safety proof or recommendation for periodic 20% cycling. Monny should restore on sleep rather than suppress sleep globally.
- [AlDente issue 1835](https://github.com/AppHouseKitchen/AlDente-Battery_Care_and_Monitoring/issues/1835) remains open/investigating: the maintainer observed roughly ten seconds of battery operation before a CalDigit TS4 regained power on M2 Pro/macOS 27. Later comments also concern distinct calibration problems; do not conflate them with the original dock failure. [Issue 1795](https://github.com/AppHouseKitchen/AlDente-Battery_Care_and_Monitoring/issues/1795) reports flicker/power oscillation on an early macOS 27 beta and is closed; it is a negative-test lead, not evidence of a universal current defect.
- [batt](https://github.com/charlie0129/batt) (GPL-2.0) and its [usage guide](https://github.com/charlie0129/batt/blob/master/docs/usage.md) distinguish adapter switching from native limits and document clamshell problems. Current upstream also reports private native targets down to 10% and draining above target on macOS 27. This is a new research lead, not Monny support or a documented Apple 20% discharge API. A low ceiling alone does not implement restoration/recharge to the user's prior target. Never restart powerd, modify global sleep settings or copy GPL code as a shortcut.
- [actuallymentor/battery](https://github.com/actuallymentor/battery) advertises discharge-to-level and an MIT root license. Its installer, shell/GUI architecture and separately sourced SMC utility are not a ready maintained Swift 6 service library; full transitive licensing and compatibility need independent review. No dependency selected/installed or code copied. Existing dependency review: [battery control](battery-control.md), [SMC control](smc-charge-control.md).

## Minimum prospective behavior and release gates

If separately authorized, one action in Battery starts a one-off session; show actual charge/target and a cancel/restore action. Disable start at/below target or when support/readings are unknown. No new tabs, sliders, scheduler, repeat cycle or CPU-burning discharge acceleration. Return ordinary power at threshold/cancel and on stale data, timeout, sleep, app loss or fault; never auto-resume. Preserve the native limit (for example 80%) and never label reconnection as confirmed charging without readings.

A privileged service would need authenticated clients, a narrow writer, durable restoration ownership, independent expiry/liveness handling, startup recovery and verified power-flow read-back. A UI timer cannot guarantee the endpoint. Initial experiments should use an open lid and dedicated adapter; monitor/dock and closed-lid support are separate gates, not assumed from that result. Reject production if the original monitor requirement cannot be met without suppressing sleep or unreliable power switching. Killed/hung helper, unplug/replug, dual supplies, restart/update/uninstall and delayed reporting need explicit acceptance. Use firmware capability checks plus named device/OS/adapter evidence, not model names or successful writes alone.

Next: decide whether there is value beyond the existing charge limit. If yes, define a read-only compatibility investigation of native behavior before separately authorizing a bounded physical prototype. No prototype/write authorization follows from this assessment.
