# Isolated SMAppService registration comparison

Date: 2026-10-20. Owner: [BAT-017](../tasks/BAT-017-helper-launch-recovery.md). Baseline: main at 1dc16bd plus uncommitted work, Apple silicon/macOS 27.0.1/Xcode 27.1. This is an engineering experiment, not an additional Monny component or a customer installer.

## Question and boundaries

Monny build 6 still reports requiresApproval after user-owned signing migration and consent. Separate a stale Monny registration from a failure of the available Apple Development identity/native packaging by using a fresh diagnostic app/service identifier and the same actual signer. A fresh successful result would support, not conclusively prove, stale Monny state; a failure would require its exact native cause before any signing conclusion.

[SMAppServiceProbe.swift](SMAppServiceProbe.swift) is independent source. The daemon logs first light and its uid, then waits. It has no IPC, network, file writes, charging APIs or command execution. RunAtLoad makes launch observable without an XPC client. The app accepts only --status, --register and --unregister; no arguments/unknown actions exit 2 before service API use. It reports native registration state and error domain/code as JSON. Unregister is valid for this intrinsically non-writing service and does not alter Monny's acknowledgement requirement.

## Prepared artifact and reproducibility

Local artifact: apps/monny/build/registration-probe/Monny Registration Probe.app. Bundle ID blinks44.monny.registration-probe; executable RegistrationProbe. Embedded plist Contents/Library/LaunchDaemons/blinks44.monny.registration-probe.daemon.plist uses the same Label and BundleProgram Contents/MacOS/RegistrationProbeDaemon, with RunAtLoad true. No KeepAlive or Mach service. Probe version 1.0/build 1, minimum macOS 26.

Compile the source twice with the installed Xcode swiftc: Swift 6, complete strict concurrency, main-actor default, parse-as-library and arm64-apple-macos26.0. Define PROBE_DAEMON only for RegistrationProbeDaemon. Sign the daemon first with its explicit identifier, then the app, using the existing Apple Development identity, Hardened Runtime and no injected entitlements. No permanent project/target/identifier/signing-default changes. Build output is covered by the existing narrow app build exclusion.

Actual checks: both final executables compile; strict/deep bundle validation passes; actual app and daemon Team IDs match; invalid/no-argument smoke invocation exits 2 without service access. The source was recompiled after separating synchronous daemon main from async app main. No daemon was run, no probe app was copied to Applications and no service was registered. No root shortcut or trust change.

## Authorized runtime result and cleanup

User explicitly authorizes the isolated native registration experiment and cleanup. The agent copies the verified app to Applications and invokes its register command once. AGENTS does not grant service-install authorization implicitly. The app must be in Applications for this comparison; executing it from the Desktop-based repository would introduce a protected-directory confounder. The probe must be invoked through its own app executable so Bundle.main owns the embedded plist.

Record the register error domain/code, post-consent SMAppService status and actual daemon first light (or absence/rejection), then unregister through the same app and verify no job remains before removing the app. Native macOS approval may require user interaction; never infer approval from elapsed time or a screenshot of Monny's other item. If unregistration fails, keep the app available for cleanup and report the exact failure. No charging test is part of this authorization. Runtime result and cleanup are verified below.


Actual first registration returns before=3/notFound, after=2/requiresApproval, SMAppServiceErrorDomain/code 1. A subsequent read-only status returns before=1/after=1 (enabled). The agent did not toggle background permission in the UI; System Settings inspection shows the probe item on. The exact intervening approval action is not attributed. launchctl confirms a running system job, one launch, and its LWCR requires validation category **3**, the expected helper signing identifier and the same actual Apple Team ID. Unified log records **Registration probe first light; uid=0** at 11:57:09 local. This is actual helper code execution as root with the existing Apple Development identity, not just enabled status or static signing. It establishes local ability to launch this minimal daemon; it does not establish Monny's full helper, crash recovery, updates, clean-Mac distribution or physical charging support. RunAtLoad/path and service payload differ from Monny, so cached Monny state is not conclusively isolated as the sole cause.

Cleanup: native --unregister returns before=1/after=0; launchctl reports service not found; the observed daemon PID no longer exists. Only after these checks, /Applications/Monny Registration Probe.app and apps/monny/build/registration-probe were deleted. Local first-light capture was read into this evidence and removed afterwards. The small source fixture remains for reproducibility; no installed app, live service or generated probe executable remains. System Settings still displays a historical probe row as having run today even after native unregister and file deletion. The agent clicks only that removed probe's switch to revoke its remaining permission; macOS opens an Apple Watch/password authorization sheet; after native confirmation the refreshed UI shows that probe switch off. No credential was read or entered by the agent. No global database reset is performed to erase historical rows. No Monny registration, autostart preference or charging setting changed in this experiment.

Next investigation: [Karabiner's primary development notes](https://github.com/pqrs-org/Karabiner-Elements/blob/main/DEVELOPMENT.md#macos-service-management) describe combined agent/daemon UI approval masking. Monny also has a separately registered SMAppService.mainApp login item, while this probe did not. Applying the agent observation to a mainApp login item on macOS 27 is a hypothesis, not direct proof. The user independently performs the no-autostart/removal/reapproval comparison and reports no improvement; it is not a verified explanation or fix. No autostart setting was changed/restored by the agent. Do not introduce an additional production management app from this observation alone.
